# RLS regression checks

Права относятся к authenticated пользователю; anon не получает защищённые данные. Роль в профиле — UI preference, не основание доступа.

| Table | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| profiles | Свой профиль и участники общих классов | Auth trigger | Собственные name/avatar/role | Только через администрирование Auth |
| classrooms | Владелец/участник | Свой класс | Владелец; teacher_id/id неизменяемы | Запрещён клиенту |
| classroom_students | Владелец/участник класса | Только join RPC по коду, за текущего пользователя | Запрещён | Собственный выход либо владелец класса |
| assignments | Владелец/участник класса | Владелец класса | Владелец; classroom_id/id неизменяемы | Запрещён клиенту |
| essays | Автор-участник видит draft; отправленные работы видят владелец/участники | Свой текст в классе, где есть membership | Автор-участник; author_id/assignment_id/id неизменяемы | Запрещён клиенту |
| reviews / teacher grades | Для доступного отправленного эссе; незавершённый отзыв — reviewer/владелец | Одноклассник, кроме автора эссе, либо владелец класса | Собственные вклады/свободные критерии; чужой verdict защищён. Владелец корректирует оценку; затем peer запись блокируется | Запрещён клиенту |
| notifications | Адресат с доступом к контексту | Владелец внутри класса; автор сохранённого review — автору эссе/владельцу | Адресат, только read | Запрещён клиенту |

`classroom_rls.sql` проверяет allow/deny от `authenticated` и `anon` в PostgreSQL с Supabase Auth schema. Нужны права `postgres` для создания тестовых Auth users и `SET ROLE`. Сценарий заканчивается `ROLLBACK`; при первой ошибке проверка должна остановиться. Используйте отдельный тестовый проект/БД, не production.

Для новой БД сначала примените `supabase_schema.sql`. Для существующей БД сначала сравните её схему с репозиторием и примените по порядку `supabase/migrations/202610010001_classroom_rls.sql`, `202610030001_review_status.sql` и `202610030002_profile_trigger_acl.sql`. Migration runner в проекте отсутствует. Пример запуска теста при наличии PostgreSQL CLI:

```powershell
psql --set ON_ERROR_STOP=1 --file supabase/tests/classroom_rls.sql
```

Подключение задавайте через стандартные переменные PostgreSQL; не помещайте credentials в репозиторий или вывод команд.

Проверяются: два класса, чужие/свои черновики и записи, подмена идентификаторов, самостоятельная смена UI role, join по коду и выход, чужие критерии/комментарии/авторство, дополнение свободного критерия, legacy review без evaluators, учительская коррекция и её блокировка для peers, переходы essay.status, уведомления и anonymous CRUD. `is_complete` сохраняет смысл отправленной, в том числе частичной, рецензии. `node supabase/tests/client_persistence.cjs` проверяет последовательные сохранения эссе, UUID, перезагрузку из серверного снимка и успех/ошибку peer/teacher review с mocked DB.

Локально сценарий выполнен на PGlite (PostgreSQL runtime вне зависимостей проекта), со stub `auth.users`/`auth.uid()` и реальными PostgreSQL grants/RLS/triggers. Проверены новая схема, upgrade исходной схемы и повторное применение миграции. Это не проверяет Supabase Auth/JWT, PostgREST или облачную конфигурацию.

Перед повторным rollout или дальнейшими изменениями в live:

1. Сверьте таблицы/колонки, `pg_policies`, table/column grants, views, functions, владельцев SECURITY DEFINER functions и exposed schemas. `private` не должна быть exposed; функции должны принадлежать доверенной роли, обходящей RLS. Миграция заменяет все policies на семи перечисленных таблицах, поэтому сначала проверьте дополнительные live policies.
2. Проверьте существующие `teacher_id`, memberships, `author_id`, `reviewer_id` и JSON-авторство. Миграция не восстанавливает происхождение ранее скомпрометированных записей. Старые `recipient_id='all'` скрываются. Черновики доступны только автору, пока он состоит в классе; владельцу класса доступны отправленные работы. До обновления клиента сохраните необходимые тексты/оценки, существующие только в старом localStorage: persist migration удаляет прежний общий cache, а D02/D03 означают, что не все его данные попали в БД.
3. Примените миграцию в тестовом проекте и выполните SQL-тест. Затем проверьте настоящими JWT двух классов и anon прямые Data API/RPC запросы, включая отвергнутые UPDATE с нулём строк, а также запись → повторная запись → reload → второй аккаунт.
4. Проверьте в UI вступление по коду, чужие deep links, обе кнопки выхода, смену аккаунта, refresh token и protected routes до загрузки session. Роль teacher — самостоятельный выбор интерфейса; права на данные даёт только владение/членство. Код вступления — передаваемое приглашение: оцените частоту попыток и смену кодов для live эксплуатации.

Classroom/assignment creation, teacher grade, peer review и essay saves теперь подтверждают запись до сообщения об успехе; общий optimistic error handling прочих мутаций и отдельные уведомления остаются (D04). Локальные проверки не доказывают, что миграции уже применены в live Supabase.
